# Спека №2 — Live-совместное редактирование (presence + курсоры + стриминг правок)

- **Дата:** 2026-06-23
- **Статус:** Draft (на ревью)
- **Зависит от:** Спека №1 (общие заметки: доступ, роли, `sharedNotes`)
- **Область:** живая синхронизация правок «как стрим», каретки всех редактирующих разными цветами, presence
- **Не входит:** сам шаринг/роли (спека №1)

---

## 1. Цель

Когда несколько участников открыли одну общую заметку, правки одного **в реальном времени** появляются у остальных, и видны **каретки** (и выделения) других людей, подсвеченные разными цветами с подписью имени — поведение уровня Google Docs / Notion.

Это самая сложная и рискованная часть проекта. Текущая модель sync (last-write-wins на уровне всего документа, фоновый WorkManager, merge по `updatedAt`) для этого **непригодна**: одновременная правача двух людей затрёт текст друг друга.

---

## 2. Три фундаментальные проблемы

1. **Транспорт.** Firestore не предназначен для высокочастотных эфемерных апдейтов (курсор двигается десятки раз в секунду) — дорого и с задержкой. Нужен низколатентный канал.
2. **Слияние текста.** Параллельные вставки/удаления должны сходиться к одинаковому результату у всех (конвергенция) без потери ввода → нужен **CRDT** или **OT**.
3. **Rich text + Aztec.** Редактор — Aztec (Android `View`), контент хранится как **Markdown**. CRDT работает над линейной последовательностью; нужно отображать операции на позиции в Aztec и обратно, плюс маппить позиции **кареток** через изменения текста.

---

## 3. Выбор транспорта

| Вариант | Латентность | Стоимость | Вердикт |
|---|---|---|---|
| Firestore (как сейчас) | средняя, батчинг | дорого на курсорах | ❌ только как fallback для финального persist |
| **Firebase Realtime Database (RTDB)** | низкая, push | дёшево для мелких эфемерных данных, есть `onDisconnect` | ✅ **рекомендую** — уже в экосистеме Firebase, не нужен новый бэкенд |
| Своя WebSocket-служба | минимальная | нужен сервер + ops | ❌ overkill для pet-проекта на Firebase |

**Решение: RTDB** для presence + курсоров + стрима операций; **Firestore `sharedNotes`** остаётся источником правды для персистентного контента (периодический «снапшот» из RTDB). Это разделяет «горячий» эфемерный канал и «холодный» долговременный.

### RTDB-структура
```
sessions/{noteId}
  presence/{uid}        // эфемерно, onDisconnect удаляет
    displayName, color, lastActive
    cursor: { anchor, head }        // позиции в ПЛЕЙН-тексте (см. §5)
  ops/{pushId}          // лог операций CRDT (append-only, подрезается)
    uid, opType, payload, lamport
  snapshot
    docState, version, updatedAt    // последний согласованный CRDT-стейт
```

## 4. Выбор алгоритма слияния: CRDT vs OT

| | OT (Operational Transform) | CRDT |
|---|---|---|
| Нужен авторитетный сервер | да (трансформирует операции) | нет (P2P/eventual) |
| Сложность реализации | высокая, тонкие баги трансформаций | средняя, но память на tombstones |
| Подходит к Firebase (без своего сервера) | плохо | **хорошо** |

**Решение: CRDT, последовательность символов (RGA / Logoot-подобный).** Без сервера-арбитра, естественно ложится на RTDB-лог операций + клиентское применение. 

Готовых зрелых rich-text CRDT для Kotlin/Android нет. Варианты реализации:
- **A. Automerge** (Rust-ядро, есть мобильные биндинги) — мощно, но JNI-интеграция и вес.
- **B. Yjs через JS-движок** — не нативно, тяжело на Android.
- **C. Своя минимальная sequence-CRDT над plain-text** (RGA: каждый символ = уникальный id `(lamport, uid)`, вставка между соседями, удаление = tombstone). — **рекомендую для v1**: контролируемый объём, достаточно для Markdown-as-text.

**Решение: C — собственная RGA над Markdown-строкой.** Форматирование (bold/list/quote) — это Markdown-разметка внутри той же строки, поэтому CRDT работает над «сырым» markdown-текстом, а Aztec рендерит его. Это упрощает модель (один линейный поток символов), ценой того, что конкурентное изменение **формата** разрешается как конкурентная правка соответствующих markdown-символов (`**`, `- `, `> `). Приемлемо для v1.

## 5. Связка CRDT ↔ Aztec ↔ каретки

- **Источник правды документа** = CRDT-строка markdown. Aztec показывает её рендер.
- Поток: пользователь печатает → `TextWatcher`/`onContentChange` даёт новый markdown → **diff** против предыдущего markdown → набор CRDT-операций (insert/delete по позициям) → применяем локально + пушим в RTDB `ops`.
- Входящие операции из RTDB применяем к CRDT → получаем новый markdown → обновляем Aztec **точечно** (без полного reset, иначе каретка прыгает и формат-стейт сбрасывается — учесть фикс из коммита `6caa2bc`).
- **Маппинг кареток:** позиции курсора храним в **plain-text смещениях** относительно markdown-строки. При применении удалённой операции сдвигаем позиции локальной и чужих кареток (классический position transform: вставка длины L в позиции p сдвигает все позиции ≥ p на +L; удаление — наоборот).
- **Отрисовка чужих кареток:** оверлей поверх Aztec — тонкая вертикальная линия + флажок с именем, цвет = `presence.color`. Выделения (anchor≠head) — полупрозрачная заливка. Реализация: кастомный `Drawable`/декоратор над `AztecText`, позиции → координаты через `Layout.getPrimaryHorizontal()`/`getLineTop()`.

**Цвета:** детерминированно по uid из палитры (8–10 различимых цветов, контраст к теме). Совпадает с цветом аватара из спеки №1 — единая identity-цветовая функция `colorForUser(uid)`.

## 6. Жизненный цикл сессии

1. Открыли общую заметку → подключаемся к `sessions/{noteId}`: ставим `presence/{uid}` (+ `onDisconnect().remove()`), подписываемся на `presence`, `ops`, `snapshot`.
2. Инициализация CRDT: грузим `snapshot` (или из Firestore-контента, если snapshot пуст), применяем накопившиеся `ops` после snapshot.version.
3. Печать → debounce курсора (~50–100мс) для presence; операции текста — без задержки (или микробатч ~30мс).
4. Throttle: presence/cursor апдейты ≤ ~10/сек.
5. **Persist:** периодически (например, раз в 3–5 сек активности или по выходу последнего редактора) пишем согласованный CRDT-стейт в Firestore `sharedNotes/{id}.content` + обновляем RTDB `snapshot`, подрезаем `ops`-лог. Это переиспользует обычный sync из спеки №1 (офлайн-устройства подтянут финальный контент).
6. Закрыли экран / disconnect → `presence` чистится, каретка пропадает у других.

## 7. Права (из спеки №1)

- **Viewer** — read-only: видит чужие каретки и live-апдейты, но не пишет операции и не показывает свою каретку как редактирующую (или показывает только presence-точку «смотрит»).
- **Editor/Manager/Owner** — полноценная правка.
- Понижение роли во время сессии → отключаем локальный ввод операций немедленно.
- RTDB rules: писать в `sessions/{noteId}` может только участник заметки с правом edit; читать — любой участник. Проверка членства — через зеркало прав (RTDB не видит Firestore; дублируем `memberIds`+роли в `sessions/{noteId}/acl`, пишет владелец/manager при изменении доступа).

---

## 8. Краевые случаи

- **Офлайн во время co-edit:** копим операции локально, при реконнекте — реконсиляция через CRDT (операции коммутативны, сойдётся). Если разошлось сильно — пересобираем из snapshot+ops.
- **Большой документ / длинная сессия:** `ops`-лог растёт → периодический compaction в snapshot, удаление применённых ops.
- **Tombstones CRDT** копятся при удалениях → ограничиваем компакцией snapshot.
- **Конкурентная правка формата** (двое делают bold на пересекающихся диапазонах) → разрешается на уровне markdown-символов; возможен «грязный» markdown — нормализуем при persist.
- **Битый snapshot / схема:** fallback на Firestore-контент как seed, лог в ошибку.
- **Курсор на удалённом тексте:** схлопывается к позиции удаления.
- **Стоимость RTDB:** throttling + compaction; мониторить.

---

## 9. Поэтапность внутри спеки (для роадмапа)

Рекомендуемый порядок инкрементов (каждый — отдельная фаза, даёт видимую ценность):
1. **Presence-only:** показываем кто сейчас в заметке (аватары «онлайн»), без курсоров и без CRDT. Низкий риск, проверяет RTDB-канал и acl.
2. **Live document streaming (без курсоров):** RGA-CRDT + diff/apply, near-realtime контент у всех. Самый сложный кусок — изолировать.
3. **Чужие каретки и выделения:** оверлей, position transform, цвета.
4. **Persist/compaction + офлайн-реконсиляция:** snapshot, подрезка ops, robustness.

(Это деление переносится в роадмап как отдельные фазы; спека №2 целиком — это последний крупный блок milestone.)

## 10. Тестирование

- **CRDT-ядро:** property-based — любые перестановки конкурентных операций сходятся к одному состоянию (конвергенция, идемпотентность, коммутативность). Это критично — без зелёных тестов ядра дальше не идём.
- **Position transform:** unit — каретки корректно сдвигаются на вставках/удалениях, в т.ч. на границах.
- **Diff markdown → ops:** unit на типовых правках (вставка слова, удаление, форматирование).
- **Integration (2 эмулятора):** одновременная печать → одинаковый результат; каретка второго видна у первого; Viewer не пишет.
- **UI/Roborazzi:** оверлей кареток (1/2/3 чужих, выделение), presence-аватары онлайн.
- **Resilience:** drop соединения в середине сессии → реконсиляция.

## 11. Риски и решения

| Риск | Митигация |
|---|---|
| Своя CRDT — источник трудноуловимых багов | Сначала зелёное property-based ядро, фаза изолирована, fallback на document-level sync из спеки №1 |
| Aztec не Compose, точечный апдейт без сброса каретки | Прототип апдейта Aztec на фазе 2 до полной интеграции; переиспользовать фикс `6caa2bc` |
| Стоимость/латентность RTDB | throttle + compaction + мониторинг |
| Маппинг rich-text позиций | CRDT над plain markdown (решение §4-C) упрощает до линейного потока |
| Объём работы | поэтапность §9; presence-only даёт ранний результат |
