# Нативный редактор заметок (замена Aztec, функционал Apple Notes)

- **Дата:** 2026-11-06
- **Статус:** Approved (дизайн согласован с пользователем по разделам; спека прошла ревью)
- **Область:** собственный редактор на платформенном `EditText` вместо Aztec; функционал Apple Notes,
  **кроме** рукописного ввода, рисования, сканера документов и аудио.

## 3. Архитектура

Контракт ViewModel не меняется: `NoteEditorViewModel` работает с Markdown-строкой
(`content` / `onContentChange`). Меняется то, что под `RichNoteBody`, и выбор пути в
`NoteEditorScreen` (§7).

```
NoteEditorViewModel ── content: String (Markdown) ──┐          без изменений (+ флаг в state, §7)
                                                    ▼
ui/editor/components/NoteBody.kt      Compose-обёртка (AndroidView)
        │  markdown ⇄ NoteDoc ⇄ Editable
        ▼
ui/editor/engine/                     Android View, без Compose
   TesseraEditText    : AppCompatEditText — хост; обёртка InputConnection; TextWatcher-нормализатор
   spans/             : BlockSpan (вид абзаца), MarkSpan (инлайн), ObjectSpan (объект)
   DocBinder          : NoteDoc → Editable, Editable → NoteDoc
   EditRules          : Enter / Backspace / автозамены / отступы / переключение стилей
   EditHistory        : undo/redo
   FormatState        : состояние у каретки → панель
        ▲
core/text/notedoc/                    чистый Kotlin, без Android
   NoteDoc, NoteBlock : модель
   NoteMarkdown       : parse(md): NoteDoc / serialize(doc): String
```

- **Почему промежуточный `NoteDoc`:** диалект и совместимость тестируются чистыми JVM-тестами
  (включая property-тест); этапы 4–5 работают с моделью. Цена — одно преобразование при выдаче
  Markdown.
- **Живая модель при редактировании — сам `Editable` со спанами** (как `NSAttributedString` в Apple
  Notes). `NoteDoc` собирается только при выдаче Markdown наружу, с дебаунсом 300 мс, как сейчас.
- **Хост — `AppCompatEditText`:** appcompat — прямая зависимость приложения; AppCompat-вариант даёт
  `OnReceiveContentListener` на API < 31, который нужен этапу 2 (картинки из IME).
- **Превью, поиск, AutoTitle** (`MarkdownPreview.kt`, `SmartSearch`, `AutoTitle`) на этапе 1 не
  переписываются: `markdownToPreviewPlainText` уже понимает `#{1,6}`, `[-*+]`, HTML-теги и отступы
  (строки `trim`-ятся). На этапе 1 туда добавляется только снятие `\`-экранирования (§5.3). Этапы 4–5
  расширяют превью под свои конструкции или переводят его на `NoteDoc` — решается в их спеках.
- **Пакет `ui/editor/engine`** — подпакет экрана редактора: движок нужен только ему.
- **Имена:** блоки модели — `NoteBlock` (в экране уже импортируется `markdownblocks.Block`).

## 4. Модель `NoteDoc` (`core/text/notedoc`)

```kotlin
data class NoteDoc(val blocks: List<NoteBlock>)   // никогда не пустой: минимум один блок

sealed interface NoteBlock {
    data class Text(val kind: ParagraphKind, val content: Inline) : NoteBlock
    data object Divider : NoteBlock
    data class Image(val src: String) : NoteBlock         // tessera-img://… как есть, включая ?w=&rot=
    data class Table(val grid: TableGrid) : NoteBlock      // существующий TableGrid / GfmTableParser
    // этапы 4–5 добавят: LinkCard(url), File(src, name)
}

sealed interface ParagraphKind {
    data object Body : ParagraphKind
    data object Title : ParagraphKind        // #
    data object Heading : ParagraphKind      // ##
    data object Subheading : ParagraphKind   // ###
    data object Mono : ParagraphKind         // строка внутри fence
    data object Quote : ParagraphKind        // >
    data class ListItem(val type: ListType, val level: Int, val checked: Boolean = false) : ParagraphKind
}
enum class ListType { Bullet, Dash, Number, Check }

data class Inline(val text: String, val marks: List<MarkRange> = emptyList())
data class MarkRange(val start: Int, val end: Int, val mark: Mark)
sealed interface Mark {
    data object Bold : Mark; data object Italic : Mark; data object Underline : Mark
    data object Strike : Mark; data object Code : Mark
    // этап 3: Highlight(color); этап 4: Link(url)
}
```

`level` — 0..4 (5 уровней); `checked` значим только для `Check`.

**Каноничный `NoteDoc`** (функция `normalize`, применяется перед сериализацией; `parse` всегда отдаёт
каноничный документ):

1. Метки одного вида, пересекающиеся или соседние, сливаются; пустые удаляются.
2. Метки обрезаются так, чтобы не начинаться и не заканчиваться пробельным символом.
3. Внутри диапазона `Code` других меток нет: метка, частично пересекающая `Code`, обрезается по его
   границам; метка, целиком накрывающая `Code`, остаётся.
4. У `Mono`-абзаца меток нет (содержимое fence — литерал).
5. `checked = false` у всех типов, кроме `Check`; `level` обрезается до 0..4.
6. `marks` отсортированы по `(start, end, порядок вида)`.
7. Пустой документ = один `Text(Body, "")`.
8. `Table` = `parseGfmTable(serializeGfmTable(grid))`: ячейки обрезаны по пробелам, строки выровнены
   по числу колонок, размеры округлены и сохраняются только при совпадении количества.
9. Между двумя подряд идущими `Table` вставляется пустой `Body`. Иначе при разборе вторая таблица
   склеилась бы с первой: `MarkdownBlocks.kt` берёт каждую следующую `|`-строку в строки таблицы.
   Ситуация достижима: пользователь удаляет выделением пустой абзац между двумя заглушками.
10. `Image` с `src`, который не проходит `IMAGE_LINE` (`tessera-img://…`), становится
    `Text(Body, "![](src)")`.
11. `\n` и `\r` в тексте абзаца, `src` и ячейках таблицы заменяются пробелом (одна строка — один
    абзац; таблица с переводом строки в ячейке не должна превращаться в пустой `Body`).
12. Границы меток не разрезают суррогатную пару: граница внутри пары сдвигается к её началу.

## 5. Markdown-диалект

### 5.1 Главное правило

**Одна строка = один абзац; пустая строка = пустой абзац (`Text(Body, "")`).** Всегда, включая
пустые строки в конце. `""` ⇄ один пустой `Body`; `"\n"` ⇄ два пустых `Body`. Исключение одно:
строки внутри fence — `Mono`-абзацы (пустая строка внутри fence = пустой `Mono`).

### 5.2 Конструкции

| Что | Запись (каноничная) | Этап | Также принимается при чтении |
| --- | --- | --- | --- |
| Название / Заголовок / Подзаголовок | `# ` / `## ` / `### ` | 1 | `####`–`######` → `Subheading` |
| Моно | строки между fence; подряд идущие `Mono` — один fence. Fence = ```` ``` ````, а если какая-то строка содержимого начинается с ≥3 бэктиков — на один длиннее самой длинной такой серии (правило CommonMark) | 1 | закрывающий fence не короче открывающего; незакрытый fence идёт до конца документа; ```` ```kotlin ```` — язык отбрасывается. Тильда-fence (`~~~`) не распознаётся |
| Точка / тире / номер | `- ` / `+ ` / `N. ` (N пересчитывается) | 1 | `* ` → точка; `N) ` → номер |
| Чек-лист | `- [ ] ` / `- [x] ` | 1 | `* [ ] `, `+ [ ] `, `[X]` |
| Вложенность | 4 пробела на уровень перед маркером | 1 | таб = 4 пробела; уровень = `ceil(пробелы / 4)`, не больше 4 |
| Цитата | `> ` | 1 | — (`>текст` без пробела — литерал, как в Aztec) |
| Разделитель | `---` | 1 | `***`, `___` |
| Инлайн | `**ж**` `*к*` `<u>п</u>` `~~з~~` `` `код` ``; запасная форма — `<b>` `<i>` `<s>` (§5.3) | 1 | только теги, которые пишем сами: `<u>`, `<b>`, `<i>`, `<s>` (+ `<mark>` с этапа 3). `<strong>`/`<em>`/`<del>`/`<strike>` — литерал (Aztec хранил набранные литералом теги как есть — их нельзя превращать в разметку). **`_к_` и `__ж__` не распознаются** (иначе `snake_case_name` и `__init__` потеряли бы подчёркивания) |
| Картинка | `![](tessera-img://id?w=&rot=)` отдельной строкой | 1 (заглушка) / 2 | без изменений |
| Таблица | GFM + `<!-- tessera:cols=…;rows=… -->` перед ней, каноничная форма `serializeGfmTable` (выравнивание и паддинг не сохраняются — как уже сейчас) | 1 (заглушка) / 2 | `GfmTableParser`; строка с `\|` без строки-разделителя — не таблица, а `Body` |
| Цветное выделение | `<mark class="purple\|pink\|orange\|mint\|blue">…</mark>` | 3 | — |
| Ссылка | `[текст](https://…)`; голый URL — текст, подсвечивается при показе | 4 | до этапа 4 — литерал |
| Карточка-превью | `<https://…>` одна на строке | 4 | до этапа 4 — литерал |
| Ссылка на заметку | `[Название](tessera-note://<noteId>)` | 4 | до этапа 4 — литерал |
| Файл / PDF | `[имя.pdf](tessera-file://<id>?mime=…&size=…)` одна на строке | 5 | — |

Внутри цитаты, заголовка и пункта списка — только инлайн: `> - x` — цитата с текстом `- x`, `- - x` —
пункт с текстом `- x`.

**Пробелы:**

- После маркера блока (`#…`, `>`, маркер списка, `[ ]`) разбор съедает ровно один пробел. Всё
  остальное — текст как есть: ведущие пробелы и завершающие `#` сохраняются, ATX-обрезки CommonMark
  нет.
- Ведущие пробелы и табы `Body`-абзаца — его текст.
- Открывающий и закрывающий fence — без отступа.

**В формат не попадает:** состояние свёрнутых разделов (иначе сворачивание меняло бы `content`, шёл бы
синк и раздел сворачивался бы у всех участников), подсветка дат/телефонов/адресов, «призрачный»
результат Math Notes (принятый результат — обычный текст), «отмеченные вниз» (глобальная настройка в
`UserPreferencesRepository`, как в iOS).

### 5.3 Инлайн-разбор, экранирование, неподвижная точка

**Разбор инлайна:** алгоритм delimiter-run из CommonMark («process emphasis», с правилами left/right
flanking и правилом «multiple of 3»), ограниченный разделителями `*`, `**`, `~~`; плюс code spans по
правилам CommonMark (разделитель — серия из N бэктиков, закрывается серией той же длины; если
содержимое и начинается, и заканчивается пробелом — по одному снимается; внутри — литерал, `\` не
обрабатывается) и распознаваемые HTML-теги из §5.2. Любой другой `<…>`, `&` — литерал
(`a <fake> tag`, `5 < 3 & 7 > 2`). `\` перед ASCII-пунктуацией вне code span и вне fence —
экранирование; перед другим символом — литерал.

**Терпимость к legacy-эмфазе.** Старый `htmlToMarkdown` переносил спаны Aztec дословно, поэтому в
хранимых заметках встречаются пары разделителей с пробелом внутри и соседние пары одного вида:
`**bold **text`, `** bold**`, `~~s ~~x`, `**a****b**`, `~~a~~~~b~~`. Aztec показывал их размеченными.
Перед инлайн-разбором строки вне code span и fence выполняется legacy-проход:

- пробелы на внутренней стороне пары `**…**` / `~~…~~` / `*…*` выносятся наружу (`**bold **text` →
  `**bold** text`);
- соседние пары одного вида склеиваются (`**a****b**` → `**ab**`, `~~a~~~~b~~` → `~~ab~~`).

Видимый текст не меняется. Сериализатор таких форм не пишет (метки обрезаются по пробелам и
сливаются, правила 1–2 §4), а запись с проверкой обратным разбором сохраняет неподвижную точку.
Случаи, которые проход не берёт однозначно (`*a**b*`), — в списке допустимых расхождений оракула.

**Запись code span:** разделитель — серия бэктиков на один длиннее самой длинной серии внутри
содержимого; если содержимое начинается или заканчивается бэктиком — добавляется по пробелу с обеих
сторон. Так любой текст `Code` имеет допустимую запись.

**Блочное экранирование** (сериализатор): если текст `Body`-абзаца после ведущих пробелов начинается
с последовательности, которую парсер принял бы за начало блока, экранируется **символ-пунктуация,
делающий её маркером** (цифра — не пунктуация, `\2` осталось бы литералом):

| Старт | Запись |
| --- | --- |
| `#{1,6}` + пробел | `\# …` |
| `-`/`+`/`*` + пробел | `\- …`, `\+ …`, `\* …` |
| `\d+[.)]` + пробел | `2024\. год`, `3\) …` |
| `> ` | `\> …` |
| ```` ``` ```` | ```` \``` ```` |
| `![](` | `\![](` |
| `<!--` | `\<!--` |
| строка целиком из `-`/`*`/`_` (≥3, допускаются пробелы) | первый символ с `\` |
| `\|` | **всегда** `\|` в начале `Body`-абзаца (иначе строка после таблицы или перед строкой-разделителем станет строкой таблицы, `MarkdownBlocks.kt`) |

Текст пункта списка, начинающийся с `[ ] ` / `[x] ` / `[X] `, пишется как `\[ ] …`.

**Инлайн-сериализация с проверкой:**

1. Абзац пишется разделителями `**`/`*`/`~~`, `<u>`, бэктиками; литеральный текст — без экранирования.
2. Результат разбирается обратно. Совпал с исходным абзацем — это и есть каноничная запись (так
   `2 * 3 * 4` и прочий legacy-текст остаются без лишних `\`).
3. Не совпал — абзац пишется **запасной формой**: метки `Bold/Italic/Strike` — тегами `<b>/<i>/<s>`,
   в литеральном тексте экранируются `\`, `*`, `~`, `` ` ``, `<`, `[`. Запасная форма обязана
   разбираться обратно всегда; это проверяет property-тест.

Порядок вложения разделителей при записи (снаружи внутрь): `<u>`, `~~`, `**`, `*`, бэктики.

**Неподвижная точка:** `parse(serialize(doc)) == normalize(doc)` для любого `doc`, и
`serialize(parse(md)) == md` для любого `md`, выданного сериализатором. Проверяется property-тестом на
случайных `NoteDoc` (случайный текст с буквами, цифрами, пробелами и пунктуацией
`*_~\`<>[]#|-+.)!`, случайные метки включая `Code` с бэктиками, все виды абзацев и уровни, пустые
строки, Mono-строки с бэктиками, блоки `Table` / `Image` / `Divider` вперемешку с текстом, `Body`
сразу после таблицы) — генератор на `kotlin.random.Random` с фиксированным seed, без новых
зависимостей.

**Нумерация** пересчитывается при записи: счётчик на уровень; сбрасывается абзацем не-списка, пунктом
меньшего уровня или пунктом того же уровня другого типа; пункты большего уровня счётчик внешнего не
сбрасывают.

**Превью:** `markdownToPreviewPlainText` снимает `\` перед ASCII-пунктуацией — **кроме** code span
и строк внутри fence (там `\` — литерал, как в разборе). Это работает и при
выключенном флаге: Aztec-путь `\` не пишет, поэтому на legacy-заметках ничего не меняется, кроме
редкого литерального `\` перед пунктуацией (§9 п.6).

## 6. Движок (этап 1)

### 6.1 Спаны

- **`BlockSpan`** — один составной спан на абзац: и данные (`ParagraphKind`), и отрисовка. Классы по
  видам: `HeadingSpan` (`MetricAffectingSpan` — размер/начертание; Title — PlayfairDisplay, логика
  `SerifH1Spanner`), `ListItemSpan` (`LeadingMarginSpan` — маркер •/–/N./чекбокс, отступ = базовый +
  `level` × шаг из `TesseraSpacing`), `QuoteSpan` (`LeadingMarginSpan` + `LineBackgroundSpan` — полоса
  и заливка как в `replaceQuoteSpans`), `MonoSpan` (`MetricAffectingSpan` моно-шрифт +
  `LineBackgroundSpan` со скруглением как `TesseraPreformatSpan`). Флаг `SPAN_PARAGRAPH`. **Абзац без
  `BlockSpan` = `Body`.** Других спанов абзацного уровня движок не ставит, синхронизировать нечего.
  `MonoSpan` и `QuoteSpan` при отрисовке смотрят на соседние абзацы: подряд идущие строки рисуются
  одним блоком (скругление только у первой и последней строки серии, без зазоров), как сейчас у
  `TesseraPreformatSpan`.
  Цвета темы передаются в конструктор как ARGB; смена темы/палитры — `DocBinder.reapplyTheme`
  пересоздаёт спаны, не трогая текст и не порождая правки.
- **`MarkSpan`** — наши подклассы (`StyleSpan`, `UnderlineSpan`, `StrikethroughSpan`, моно + фон для
  `Code`), флаг `SPAN_EXCLUSIVE_EXCLUSIVE`. Продолжение разметки при наборе делают typing attributes
  (§6.6), а не флаги спана.
- **`ObjectSpan`** — `ReplacementSpan` на одиночном `U+FFFC`, занимающем свой абзац; держит исходный
  `NoteBlock` (`Image` / `Table` / `Divider`). Этап 1: разделитель рисуется линией
  (`outlineVariant`), картинка и таблица — заглушкой (иконка + подпись «Изображение» / «Таблица»,
  строки en+ru, высота одной строки + отступы). Атомарен: каретка не встаёт внутрь; Backspace сразу
  после него сначала выделяет объект, второй — удаляет. Сериализуется исходным блоком (таблица — в
  каноничной форме `serializeGfmTable`).
- **Пустой последний абзац не-`Body`** (Enter в конце чек-листа, legacy `"- a\n- "`) имеет нулевую
  длину и не может держать спан. Такой абзац содержит служебный `U+200B`, помеченный `SentinelSpan`:
  он держит `BlockSpan` и даёт отрисовать маркер. Нормализатор удаляет служебный символ (только
  помеченный `SentinelSpan`, а не любой `U+200B` из legacy-текста или вставки), как только в абзаце
  появился другой текст. Сериализатор и `FormatState` его игнорируют, каретка ставится после него,
  Backspace с кареткой сразу после него считается «Backspace в начале абзаца», а
  `getCursorCapsMode` в обёртке `InputConnection` считает позицию после него началом абзаца (иначе
  ломается автозаглавная буква).

### 6.2 Инварианты

Нормализатор проверяет и чинит после каждой правки, только на затронутых абзацах:

1. У абзаца не больше одного `BlockSpan`, ровно по его границам.
2. IME-правки (автокоррекция, подсказки, composing) не меняют `BlockSpan` абзаца — закрывает баг
   «автокоррекция превращает абзац в H1». Репро из `b5c80c4` (`RichNoteBodyExactNoteMarkupTest`,
   `RichNoteBodyParagraphAutocorrectHeadingTest`) переносятся на новый движок и обязаны пройти.
3. В `NoteDoc` попадают только `BlockSpan` / `MarkSpan` / `ObjectSpan`.
4. Чужие **оформляющие** спаны — не наши `CharacterStyle` / `ParagraphStyle` / `ReplacementSpan`
   (из вставки, drag & drop, `commitText` со стилями) — удаляются, **кроме** `SuggestionSpan`,
   `SuggestionRangeSpan` и спанов с флагом `SPAN_COMPOSING`. `SuggestionRangeSpan` — `@hide`,
   сверяется по имени класса. `SpellCheckSpan` (тоже `@hide`) не `CharacterStyle` и под удаление не
   попадает. Служебные спаны
   фреймворка (`NoCopySpan`, `SpanWatcher`/`TextWatcher`, выделение, состояние `MetaKeyKeyListener`)
   не трогаются никогда. Что видно на экране — то и сохраняется.
5. `U+FFFC` существует только как отдельный абзац с `ObjectSpan`; `U+FFFC` без спана удаляется.
   `U+200B` существует только по правилу §6.1.

### 6.3 Два механизма правок

1. **Перехваченные команды** — явные операции над `Editable`: Enter, Backspace в начале абзаца, Tab,
   кнопки панели. Перехват во всех путях: обёртка `InputConnection` (`commitText("\n")`,
   `sendKeyEvent(ENTER/DEL)`, `deleteSurroundingText(1, 0)` — Gboard шлёт его, Samsung — `DEL`) и
   `onKeyDown` для аппаратной клавиатуры.
2. **Нормализатор** в `TextWatcher.afterTextChanged` (с guard от рекурсии) — всё остальное: вставка из
   буфера, замены IME, удаление выделения через абзацы. Новые абзацы без вида берут вид абзаца, в
   котором началась вставка (как в Apple). Здесь же автозамены (§6.5) и typing attributes (§6.6).

### 6.4 Enter и Backspace

Enter в начале/середине абзаца делит строку, обе части сохраняют вид. В конце:

| Где | Непустой абзац | Пустой абзац |
| --- | --- | --- |
| пункт списка / чек-листа | новый пункт того же типа и уровня; в чек-листе — неотмеченный | `level > 0` → уровень −1; `level = 0` → `Body` |
| цитата | новая строка цитаты | → `Body` |
| заголовок любого уровня | новый абзац `Body` | новый абзац `Body` |
| моно | новая `Mono`-строка | новая `Mono`-строка (выход — через панель, как в Apple) |

Backspace в начале абзаца, без выделения:

1. Вид не `Body`: у пункта с `level > 0` уровень уменьшается на 1, иначе вид сбрасывается в `Body` на
   месте, текст остаётся.
2. `Body`, а предыдущий абзац — объект: объект выделяется. Следующий Backspace удаляет абзац объекта
   целиком, вместе с переводом строки; каретка остаётся в начале своего абзаца.
3. `Body`: склейка с предыдущим абзацем, итог берёт вид предыдущего. В начале документа ничего не
   происходит.

Enter в середине отмеченного пункта: первая часть сохраняет отметку, вторая становится новым
неотмеченным пунктом. Enter в начале непустого пункта: выше появляется пустой неотмеченный пункт.

Удаление/замена выделения через несколько абзацев: итоговый абзац берёт вид первого.

Backspace в середине абзаца стирает графемный кластер целиком: 👍🏽, 🇷🇺, ZWJ-эмодзи и keycap
уходят за одно нажатие (`android.icu.text.BreakIterator`). При активном composing стирается символ
перед composing-регионом, как в `BaseInputConnection`.

### 6.5 Автозамены при наборе

Только в начале `Body`-абзаца; триггер — введённый с клавиатуры пробел сразу после маркера; при
вставке из буфера не срабатывают:

| Набор | Результат |
| --- | --- |
| `* ` | точка |
| `- ` | тире (как в Apple) |
| `1. ` / `1) ` | номер |
| `[] ` / `[ ] ` | чек-лист |
| `# ` / `## ` / `### ` | Название / Заголовок / Подзаголовок |
| `> ` | цитата |
| ```` ``` ```` + пробел | моно |

Автозамена — отдельный шаг истории: undo сразу после неё возвращает набранные символы.

### 6.6 Форматирование и typing attributes

- **Typing attributes** — набор меток для следующего набранного текста. По умолчанию — метки символа
  перед кареткой (в начале абзаца — первого символа абзаца), как в Apple. **`Code` не
  наследуется**: иначе после legacy-кода в конце абзаца весь набранный текст оставался бы кодом, а
  кнопки, чтобы снять его, нет. Исключение — каретка внутри code span, когда `Code` есть и у
  символа до каретки, и у символа после: тогда набор продолжает код. Метка, частично пересекающая
  `Code`, обрезается по его границам уже в `Editable` (правило 3 §4), чтобы на экране было то же,
  что сохранится.
  Кнопка инлайн-метки без выделения переключает метку в этом наборе. Набор сбрасывается к умолчанию
  при перемещении каретки.
- **Применяются только к реально вставленным символам.** IME часто заменяет composing-регион целиком
  (Gboard заново открывает композицию над словом, когда каретка в него входит), и такая замена может
  смахнуть метки существующих символов. Поэтому нормализатор в `beforeTextChanged` запоминает метки
  заменяемого диапазона, а в `afterTextChanged` сравнивает старый и новый текст диапазона. Общие
  префикс и суффикс — это старые символы, им возвращаются прежние метки. Только средняя, новая часть
  получает typing attributes. Так набор в конце «**Т**екст» не снимает жирный с «Т», а «выключить
  жирный в конце жирного слова» работает.
- Инлайн-кнопка с выделением: весь фрагмент уже размечен → снять, иначе добавить на весь фрагмент.
- Кнопка вида абзаца — на все абзацы, затронутые выделением; если все уже этого вида → `Body`.
  Переключение в/из списка сохраняет текст; `level` при выходе из списка обнуляется.
- Отступы: кнопки «вправо»/«влево», Tab / Shift+Tab с аппаратной клавиатуры; действуют на пункты
  списков, затронутые выделением; диапазон 0..4. Маркеры на всех уровнях одинаковые (•, –, N.).
- Инлайн-код поддерживается в модели и отрисовке (legacy-заметки), отдельной кнопки нет — как в Apple.
  Кнопка «код» на панели = вид `Mono`.
- Горячие клавиши: Ctrl+B / I / U, Ctrl+Z, Ctrl+Shift+Z.

### 6.7 Undo / redo

`EditHistory` — снимки `(markdown, selection)`: серия ввода склеивается по паузе ~500 мс; команды
панели и автозамены — отдельные шаги; лимит 100. Undo/redo пересобирает `Editable` из снимка через
`DocBinder` и считается пользовательской правкой (выдаётся наружу). Внешняя пересборка (§6.9)
очищает историю: undo через изменения соавтора/синка не поддерживается.

### 6.8 Буфер обмена

- Копирование/вырезание внутри Tessera: в системный буфер — plain text; в памяти процесса — пара
  `(plainText, markdownFragment)`. При вставке, если plain text в буфере совпадает, вставляется
  фрагмент с форматированием (`NoteMarkdown.parse` → `DocBinder`).
- Вставка из других приложений — всегда plain text (`onTextContextMenuItem(paste)` вставляет как
  `pasteAsPlainText`); строки берут вид абзаца в точке вставки.
- Картинка из буфера / IME rich content под флагом на этапе 1 не принимается (этап 2).

### 6.9 Выдача Markdown наружу, внешние обновления, эхо

- **Выдача только на пользовательской правке.** `onMarkdownChange` вызывается (через дебаунс 300 мс)
  только после правки от пользователя: ввод, IME, команды, вставка, undo/redo. Загрузка, внешняя
  пересборка, `reapplyTheme`, смена `editable` и dispose ничего не выдают; на dispose выдаётся только
  отложенная пользовательская правка, если она есть. Поэтому legacy-заметка, открытая и закрытая без
  правок, не меняется. При первой правке вся заметка переписывается в каноничную форму — это
  ожидаемо, видимый текст не меняется (гарантируют §8).
- **Эхо и гонка с синком** (цель — как у `RichNoteBody` сейчас). `NoteBody` хранит
  `lastLoadedMarkdown` (сырой Markdown, который он последним загрузил или выдал) и флаг
  `hasPendingUserEdit`: он ставится при пользовательской правке и снимается при выдаче.
  - Пришедший `markdown`, равный `lastLoadedMarkdown`, игнорируется.
  - Отличный применяется, только если `hasPendingUserEdit == false`. Иначе он пропускается:
    отложенная выдача сама согласует состояние, и стёртый символ не «возвращается».
  - Живой документ с сырой строкой **не сравнивается**: legacy-заметка в неканоничной форме
    (`* x`, `1. 1.`) никогда бы не совпала, и правки соавторов терялись бы.
  - Применение пересобирает `Editable` с сохранением выделения по смещению (обрезанного до длины),
    обновляет `lastLoadedMarkdown` и очищает `EditHistory`.

### 6.10 Только чтение, доступность, прокрутка

- `editable = false` (зритель общей заметки): `keyListener = null`, `setTextIsSelectable(true)`.
  Ввода нет, чекбоксы не переключаются, выделение и копирование работают, текст скроллится сам.
- TalkBack: текст читается как у обычного `EditText`; на каждый чекбокс — виртуальный узел
  (`ExploreByTouchHelper`) с состоянием «отмечено / не отмечено», переключение двойным тапом.
  Тап-зона чекбокса: ширина равна `LeadingMargin` пункта, высота — строке, но не меньше 48dp. Тап по
  первым буквам ставит каретку и чекбокс не переключает. Долгое нажатие на чекбокс выделяет слово и
  тоже не переключает его.
- Прокрутка и подъём каретки над клавиатурой — как в быстром пути `RichNoteBody`: редактор занимает
  область и скроллится сам, `caretRectOf` → bring-into-view.

### 6.11 Визуал

Цвета — только `MaterialTheme.colorScheme.*`, в спаны передаются как ARGB. Типографика:

| Вид | Стиль |
| --- | --- |
| Название | как текущий H1 редактора: PlayfairDisplay, ≈ 26sp |
| Заголовок | как текущий H2 редактора: PlayfairDisplay, ≈ 20sp (`SerifH1Spanner` красит serif и H1, и H2; мокап с Inter 600 расходится с кодом — оставляем то, что пользователь видит сейчас) |
| Подзаголовок | `MaterialTheme.typography.titleLarge`: Inter W600, 18sp — между Заголовком и основным |
| Основной | `bodyLarge`: Inter W400, 15sp (текущая база редактора) |
| Моно | размер основного, `Typeface.MONOSPACE`, фон/цвет как текущий `replacePreformatSpans` |
| Цитата | основной текст, полоса/цвет/заливка как текущий `replaceQuoteSpans` |
| Маркеры списков | цвет и радиус как текущие `replaceBulletSpans` / `replaceOrderedListSpans`; чекбокс — как `EditorCheckboxTheming` |

Отступы — `TesseraSpacing`. Каждый вид проверяется в light и dark.

**Вертикальные отступы блоков** (по CSS макета `design/mockups/shared.css`, `.editor-*`). Ставятся
на краях блоков и серий, а не после каждой строки. В нашей модели одна строка — один абзац, и
отступ после каждой Body-строки разредил бы обычный текст относительно Aztec и Apple Notes.

| Блок | Отступ, dp |
| --- | --- |
| Название | сверху 12, снизу 8 |
| Заголовок, Подзаголовок | сверху 12, снизу 6 |
| Серия пунктов списка (любые типы подряд) | 10 по краям серии; 3 сверху и снизу каждого пункта |
| Серия цитаты | 10 по краям снаружи; 4 внутри полосы у первой и последней строки |
| Серия моно | 10 по краям, снаружи фона |
| Объект | 10 сверху и снизу |
| Body ↔ Body | 0 |

Соседние отступы схлопываются, как в CSS: берётся max, а не сумма. У первого абзаца документа нет
отступа сверху, у последнего — снизу. Отступы зависят от соседей и пересчитываются тем же механизмом,
что края серий моно и нумерация.

## 7. Интеграция (этап 1)

- **Флаг.** `useNativeEditor: Flow<Boolean>` в `UserPreferencesRepository` (по умолчанию `false`).
  `NoteEditorViewModel` кладёт его в `NoteEditorState`. Переключатель «Новый редактор (beta)» — строка
  в Settings, видимая, только когда `SettingsScreen` получил `showDebugOptions = true` (новый
  параметр, по умолчанию `false`). Значение вычисляется на месте вызова в навигации:
  `(context.applicationInfo.flags and ApplicationInfo.FLAG_DEBUGGABLE) != 0`. `BuildConfig` в проекте
  не генерируется, правка Gradle не нужна. Существующие скриншот-тесты Settings параметр не передают,
  их golden не меняются.
- **Выбор пути в `NoteEditorScreen`.** При `useNativeEditor = true` экран всегда идёт по
  «быстрому» пути, с внутренней прокруткой, без внешнего `verticalScroll`: и для чтения, и при
  наличии таблиц. Вместо `EditorBody` вызывается `NoteBody` (он всегда заполняет область и
  скроллится сам, параметра `scrollable` нет), весь документ — один `NoteBody`, таблица —
  заглушка-объект. При `false` — текущий код без изменений.
- **`NoteBody`** (`ui/editor/components/NoteBody.kt`): `markdown: String`,
  `onMarkdownChange: (String) -> Unit`, `onActionsReady: (RichBodyActions) -> Unit`,
  `onFormatStateChanged: (FormatState) -> Unit`, `editable: Boolean`, `onFocusChanged`, `modifier`.
- **`RichBodyActions`.** `NoteBody` реализует существующий интерфейс. Новые методы с реализацией по
  умолчанию: `toggleSubheading()`, `toggleDashList()`, `indent()`, `outdent()` — no-op;
  `formatState(): FormatState = FormatState.Empty`. Маппинг существующих методов: `toggleHeading1/2/3` →
  Название / Заголовок / Подзаголовок, `toggleHeading4–6` → Подзаголовок, `toggleCode` → `Mono`,
  `toggleParagraph` → `Body`, `insertHorizontalRule` → `Divider` после абзаца с кареткой.
  `activeFormats()` у Aztec-пути остаётся. Под флагом `insertTable` / `onInsertImage` /
  `onCaptureImage` / `insertImage` не вызываются: соответствующие пункты панели скрыты (§7, панель).
  Интерфейс переезжает из `RichNoteBody.kt` на этапе 2.
- **`FormatState`**: вид абзаца у каретки (`Mixed`, если выделение задевает разные виды), активные
  метки (активна, если покрывает всё выделение; без выделения — typing attributes), `canIndent`,
  `canOutdent`, `canUndo`, `canRedo`.
- **`EditorFormatBar` / `MarkdownFormatMenu`.** Новый необязательный параметр `nativeEngine: Boolean =
  false` (прежний дефолт — Aztec-путь и его golden не меняются) и `formatState: FormatState?`. При
  `nativeEngine = true`:
  - активность кнопок берётся из `formatState`;
  - меню показывает Название / Заголовок / Подзаголовок / Основной / Моно / Цитата вместо
    H1–H6 / Paragraph;
  - добавлены «Тире» и «Отступ вправо / влево»;
  - скрыты «Вставить таблицу», «Картинка» и «Камера».

  Иконки — Lucide или material, как у соседей. Строки — в `values` и `values-ru`: Название, Заголовок,
  Подзаголовок, Основной текст, Моноширинный, Тире, Отступ вправо, Отступ влево, Новый редактор
  (beta), Изображение, Таблица.

**Оракул Aztec ↔ новый движок** (Robolectric; живёт до удаления Aztec на этапе 2):

- **Вход:** корпус выше без строк с таблицами (таблицы Aztec-путь рендерит отдельным `TableBlockEditor`,
  не через `markdownToHtml`). Плюс дамп реальных заметок, если он доступен (`adb` + Room-база с
  устройства).
- **Сравнение:** построчно видимый текст и вид строки (Название / Заголовок / пункт списка / чекбокс
  ± / цитата / моно / обычный) у `AztecText` (текущий `markdownToHtml` → `fromHtml`) и у нового
  `Editable`.
- **Нормализация перед сравнением:** NBSP-строки → пустые; убрать `U+200B`, `U+FFFC` и заглушки
  объектов.
- **Допустимые расхождения** (явный список в тесте, каждое — отдельный кейс с комментарием):
  - конструкции, которые Aztec показывал литералом, а новый диалект распознаёт: `* `, `+ `, `N) `,
    `###`–`######`, `***`/`___`, `[X]`, отступ перед маркером;
  - эмфаза, где новый разбор следует flanking, а старый регэксп — нет (`2 * 3 * 4`: в Aztec курсив,
    у нас литерал);
  - набранные литералом теги `<b>`, `<i>`, `<s>` (Aztec хранил их как текст, у нас — разметка);
  - соседние курсивы `*a**b*` (legacy-проход §5.3 их не склеивает однозначно);
  - ведущие пробелы строки: Aztec при загрузке схлопывает пробел в начале абзаца (правило HTML), а
    движок хранимый пробел сохраняет (`** bold**` → Aztec «bold», у нас « bold»). Допустимо, только
    если строки отличаются **исключительно** ведущими пробелами;
  - 1–2 пустые строки в конце документа, которые Aztec показывает после `fromHtml` (его
    end-of-buffer marker), если сам Markdown не кончается на `\n`;
  - строка из ≥4 бэктиков внутри legacy-кода закрывает fence (правило CommonMark), хвост разбирается
    как обычный текст;
  - `\` перед пунктуацией вне кода.

Тесты пишутся от инвариантов фичи и гоняются на устройстве. Запрещено ради зелёного прогона: `@Ignore`,
ослабление ассертов, `@Suppress`, перезапись golden.

## 9. Приёмка этапа 1

1. Под флагом существующие заметки открываются с теми же видимыми строками и видами, что в Aztec:
   оракул зелёный (с явным списком допустимых расхождений) на корпусе и на дампе реальных заметок,
   если он доступен.
2. Открыть и закрыть заметку без правок не меняет `content`: нет лишнего `updatedAt` и синка.
3. Каждая конструкция этапа 1 переживает «правка → сохранение → переоткрытие».
4. On-device набор зелёный, включая репро автокоррекции.
5. Заметка на 1000 абзацев открывается ≤ 300 мс на тестовом устройстве, ввод без видимых лагов —
   замер, результат в отчёте.
6. С выключенным флагом поведение и golden не изменились (существующие тесты зелёные). Единственное
   общее изменение — снятие `\` в превью (§5.3).

| Риск | Мера |

## 11. Ориентиры для этапов 2–5 (обязательны, детали — в их спеках)

- **Этап 2.** Объект = абзац из `U+FFFC` + `ObjectSpan`. Картинка рисуется спаном (размер — из
  `w`/`rot`; переиспользуются `ImageSelectionGeometry`, `TesseraImageLoader`; локальные drawable —
  синхронно, `DENSITY_NONE` — memory `aztec_async_image_sizing`, `aztec_image_intrinsic_sizing`).
  Картинки из IME/буфера — через `OnReceiveContentListener`. Таблица: `ObjectSpan` резервирует
  высоту, поверх `EditText` в общем контейнере позиционируется редактор таблицы (переиспользуется
  `TableBlockEditor`), высота спана синхронизируется с измеренной высотой оверлея. Если спайк покажет,
  что оверлей не держит IME или скролл, — запасной вариант: текущая схема «текстовые сегменты + блок
  таблицы», выделение через таблицу тогда не поддерживается.
- **Этап 3.** Свайп по пункту — горизонтальный жест в зоне строки с порогом, не конфликтующий с
  выделением; перетаскивание — long-press на маркере/чекбоксе, перенос абзаца вместе с вложенными
  пунктами; сворачивание — стрелка у заголовка, скрытие диапазона раздела `ReplacementSpan` нулевой
  высоты, состояние только в памяти экрана.
- **Этап 4.** Ссылка на заметку хранит `noteId`; при показе текст ссылки — актуальное название
  заметки (хранимый текст — fallback для удалённой). Метаданные карточек — локальный кэш, не в
  `content`.
- **Этап 5.** Math Notes — парсер выражений `+ − × ÷ ^ ( ) %` и переменных `x = 5` в пределах
  заметки; результат показывается «призраком» после `=`, принимается вводом или тапом. Поиск и замена —
  панель над клавиатурой, подсветка совпадений временными спанами (не `MarkSpan`).
